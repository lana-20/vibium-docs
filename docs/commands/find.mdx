# vibium find

Locate an element and bind it to a ref. `find` takes either a CSS selector or
one of eight semantic locators that match the way a person would describe the
element — by its text, its label, its ARIA role.

:::tip[Verified against a live browser]
Every example on this page is real terminal output captured from **vibium
v26.8.21**, run against this site's own
[playground fixture](pathname:///vibium-docs/fixtures/playground.html) — a fixed page served
from this repo, so the output cannot drift when someone else's markup changes.
Every example is reproducible against that URL exactly as shown.
:::

## Synopsis

```
vibium find [selector]
vibium find <locator> <value>
```

## Flags

| Flag | Argument | Description |
| --- | --- | --- |
| `--all` | — | Find all matching elements |
| `--limit` | `int` | Maximum number of elements to return (with `--all`) (default 10) |
| `--timeout` | `timeout` | Max time to wait, e.g. 5s or 5000 (bare number = milliseconds) (default 30s) |

Global flags apply as well — see [Global flags](/docs/global-flags).

## By CSS selector

With no locator, the argument is a CSS selector. `find` returns **only the first
match** unless you pass `--all`:

```sh
$ PLAYGROUND=https://lana-20.github.io/vibium-docs/fixtures/playground.html
$ vibium go "$PLAYGROUND"
Navigated to https://lana-20.github.io/vibium-docs/fixtures/playground.html

$ vibium find "a"
@e1 [a] "Home"

$ vibium find "a" --all
@e1 [a] "Home"
@e2 [a] "Docs"
@e3 [a] "About"
@e4 [a] "Next page"

$ vibium find "a" --all --limit 2
@e1 [a] "Home"
@e2 [a] "Docs"
```

## Semantic locators

Eight subcommands match on meaning rather than structure. They are usually more
durable than CSS selectors, because they survive the restyling and class-name
churn that breaks selectors.

### `vibium find text`

Match on visible text content.

```sh
$ vibium find text "Sign In"
@e1 [button type="submit"] "Sign In"
```

### `vibium find label`

Match an input by its associated `<label>` — the text a person sees next to the
field, rather than anything in the input itself.

```sh
$ vibium find label "Email"
@e1 [input type="email"] placeholder="you@example.com"
```

### `vibium find placeholder`

Match an input by its placeholder attribute.

```sh
$ vibium find placeholder "Search docs"
@e1 [input type="search"] placeholder="Search docs"
```

### `vibium find role`

Match by ARIA role. Add `--name` to disambiguate by accessible name.

```sh
$ vibium find role button
@e1 [button type="submit"] "Sign In"

$ vibium find role heading
@e1 [h1] "Playground"
```

The page has five buttons, and a bare `role button` returns only the first.
`--name` picks the one you meant:

```sh
$ vibium find "button" --all
@e1 [button type="submit"] "Sign In"
@e2 [button type="button"] title="Close dialog"
@e3 [button type="button"] "Count"
@e4 [button type="button"] "Locked"
@e5 [button type="button"] "Reveal panel"

$ vibium find role button --name "Count"
@e1 [button type="button"] "Count"
```

Note `@e4` above: `find` returns the disabled "Locked" button like any other
match. Matching an element says nothing about whether it can be acted on — see
[`vibium is enabled`](/docs/commands/is).

### `vibium find testid`

Match on `data-testid`. The most stable locator of all, since the attribute
exists only for automation and nothing else should be changing it.

```sh
$ vibium find testid "submit-btn"
@e1 [button type="submit"] "Sign In"
```

### `vibium find alt`

Match an image by its `alt` text.

```sh
$ vibium find alt "Company logo"
@e1 [img] src="logo.svg"
```

### `vibium find title`

Match by the `title` attribute — useful for icon-only controls, which often have
no text at all.

```sh
$ vibium find title "Close dialog"
@e1 [button type="button"] title="Close dialog"
```

### `vibium find xpath`

Match by XPath, for the cases the other locators cannot express.

```sh
$ vibium find xpath "//a[@href='#docs']"
@e1 [a] "Docs"
```

## When nothing matches

`find` waits for the element until `--timeout` expires, then writes an error to
stderr and **exits 1** — so it is safe to use in a conditional without parsing
output:

```sh
$ vibium find ".missing" --timeout 2s
Error: element not found: .missing (timeout 2s)
$ echo $?
1

$ vibium find text "Nope" --timeout 2s
Error: element not found: text=Nope (timeout 2s)
$ echo $?
1
```

The error names the locator in the form it was resolved (`text=Nope`), which is
worth knowing when debugging a semantic locator that did not match.

## JSON output

```sh
$ vibium find "a" --json
{"ok":true,"result":"@e1 [a] \"Home\""}

$ vibium find "a" --all --json
{"ok":true,"result":"@e1 [a] \"Home\"\n@e2 [a] \"Docs\"\n@e3 [a] \"About\"\n@e4 [a] \"Next page\""}
```

As with [`map`](/docs/commands/map), matches arrive as one newline-joined string
in `result` rather than as an array.

## Refs are shared with `map`

`find` writes into the same ref table as [`vibium map`](/docs/commands/map), and
always numbers its results from `@e1`. A `find` after a `map` therefore rebinds
`@e1` — see [Refs are rebound by `find`](/docs/commands/map#refs-are-rebound-by-find-too)
for a worked example.
